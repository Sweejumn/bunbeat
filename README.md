# RUN BPM · 基于 BPM 的跑步音乐播放器（Web 应用）

**让音乐跟随你的跑步节奏。**

上传自己的音乐 → 自动识别每首歌的 BPM → 选择运动模式与目标节奏 → 按差距推荐歌曲 →
变速统一到目标 BPM（**保持音高不变**）→ 节拍器逐拍对齐真实拍点 → 连续播放。
节拍对不上？不用猜：**打拍校准 + 相位微调 + 拍点标尺**，眼见为实、所见即所听。

> 本仓库是完整可运行的项目：FastAPI + SQLite 后端、React 前端、librosa 分析、
> FFmpeg 时间拉伸。支持本机运行、局域网手机访问、一键部署到云服务器。

## 功能特性

### 音乐导入与分析

- 🎵 **批量上传**：一次拖入/选择多首；支持 MP3 / WAV / M4A / AAC / OGG / FLAC / OPUS；
  单文件上限默认 **100 MB**（`RUNBPM_MAX_UPLOAD_MB` 可调）。
- 🔍 **异步 BPM 分析**：上传后立即排队，页面顶部实时显示「正在分析 2/5（剩 n 首）」；
  每首歌显示 **BPM 与可信度**，失败可点**重试**。
- 📝 **手动改 BPM**：表格里的 BPM 数字可直接点击修改——检测不准时这是最快的兜底方案。
- 🧠 **检测算法**：librosa 节拍追踪 + 自相关精修（误差约 ±0.5%），内置
  **2 倍 / 0.5 倍八度修正**与 **1.5 倍三连音脉冲修正**；相位可靠性由两个独立信号交叉验证。
- 🗑️ 删除歌曲时**连带清理**分析/处理产物，不留垃圾文件。

### 运动模式与推荐

- 🏃 **一根滑块覆盖 4 个区间**：走路 100–120 · 慢跑 120–145 · 跑步 145–165 · 快跑 165–185
  （区间底色：天蓝/翠绿/琥珀/红），拖到哪就是哪档；4 个区间卡片可一键跳转。
- 🎯 **任意目标 BPM**：区间外（<100 或 >185，含 40–300）在右侧输入框手动输入。
- 📋 **推荐列表**：按**相对差距百分比**排序（越接近越靠前）；每行显示
  `BPM 目标+差`（如 `155+5`）、方向箭头/等号、带符号百分比；**颜色分级**一目了然：
  `<5%` 绿、`5–8%` 琥珀、`>8%` 红；**`>12%` 显示红 ✕**（变速失真风险大）。
- ✅ **自动勾选**：生成推荐时自动选中所有可变速歌曲（✕ 除外）；「全选」= 全选可变速项。

### 变速处理

- ⏩ **保持音高的时间拉伸**：FFmpeg `atempo`（WSOLA 类算法，业界成熟），不会出
  「花栗鼠」效果；变速范围 **1/3× – 3×**（超出即拒绝，防止严重失真）。
- 🗃️ **磁盘缓存**：结果按 `歌曲 + 目标BPM` 缓存，重复请求秒回，不重复跑 FFmpeg。
- 🔄 处理队列限并发（默认 1 路变速 + 2 路分析），进度条实时显示，失败自动跳过并提示。

### 播放器与节拍对齐（本项目的重头戏）

- ▶️ 播放/暂停、上一首/下一首、进度拖动、音量；处理完成后**自动连续播放整个歌单**，循环无缝。
- 🥁 **节拍器默认开启**：浏览器 Web Audio 生成清脆「嗒」声（D6 方波）；不是固定间隔，
  而是**逐拍落在分析出的真实拍点上**（全曲节拍地图，播放到结尾也不漂移）。
- 📏 **拍点标尺常驻**：绿色竖线 = 每个拍点，横向流过中心线（当前拍）；暂停即静止。
  黄条 = 你手动打拍的痕迹（保留最近 20 次）。
- 🎯 **偏差微调滑杆（±50% 拍距）**：点击听起来偏早/偏晚时整体平移节拍；
  **绿条会随滑杆实时移动**——所见即所听；带「归零」一键复位，偏好本地保存。
- 👆 **打拍校准（手动挡）**：自动对齐不可靠时，靠耳朵点按 8 下 → 算出 BPM →
  一键设置；还能把任意播放位置设成「首拍」。详见[使用手册](#使用手册)与
  [拍点对齐系统](#拍点对齐系统原理深挖)。
- 🎚️ **三条音量滑杆**：音乐音量 / 节拍器音量（音量和拍子并排一行）/ 偏差（单独一行）。
- 🔧 **节拍模式可切换**：固定拍子（完全等距，默认）/ 轻跟随（±5%）/ 跟随起音（±12%）。
- 📱 **移动优先**：底部固定播放条，手机上拇指操作；页面底部留白保证内容不被播放条遮挡。

### 可靠性 / 运维友好

- 前后端均为单进程零外部依赖（数据库是 SQLite 文件），一条命令即可跑起来。
- 内置**自诊断**：后端每 30 秒记录 CPU/内存/磁盘，前端每 10 秒记录帧率/DOM/内存，
  出问题看日志即可定位。
- 生产模式由后端直接托管前端静态文件；提供 systemd + nginx 部署模板（见[部署](#部署到云服务器给其他人用)）。

## 核心概念与术语

先把几个词说清楚，后面的手册才不绕：

| 术语 | 含义 | 界面里在哪 |
|---|---|---|
| **BPM** | Beats Per Minute，每分钟拍数，节奏快慢 | 歌曲表、模式滑块、推荐、播放条 |
| **拍点（beat）** | 一首歌里「每一拍」发生的时刻（秒） | 标尺上的绿色竖线 |
| **首拍 / 相位（phase）** | 第一拍落在歌曲的第几秒；决定整组拍点相对音频的平移 | 「🎯 设首拍」 |
| **节拍地图** | 全曲每个拍点的时间数组，节拍器逐拍点击的依据 | —（内部数据） |
| **时间拉伸** | 变速但音高不变（atempo） | 「变速并播放」 |
| **相位微调** | 在已对齐的拍点上整体前后平移（不超过半个拍距） | 「🎯 偏差」滑杆 |
| **打拍校准** | 手动点按 8 下，用你的耳朵定义 BPM | 播放条「校准」区 |

一个关键认知：**BPM（速度）只告诉你拍子多快，没告诉你第一拍在哪**。
两首 150 BPM 的歌，鼓点可以差半拍。所以本项目对齐拍点靠的是**完整节拍地图 +
首拍位置**，而不是「从 0 秒起每 0.4 秒嗒一下」的偷懒方案。

## 技术栈与架构

| 层 | 技术 | 说明 |
|---|---|---|
| 前端 | React 19 + TypeScript + Vite 8 + Tailwind CSS 4 | 无 UI 框架依赖，组件手写 |
| 后端 | Python 3.12 + FastAPI + Uvicorn | 单进程；任务队列在进程内 |
| 数据库 | SQLite（标准库 sqlite3，无 ORM） | 单文件，WAL 模式 |
| BPM/节拍检测 | librosa ≥0.10（含 numba） | 22.05 kHz 分析 |
| 时间拉伸 | FFmpeg `atempo` | 经 `imageio-ffmpeg` 自带静态构建 |
| 元数据 | mutagen | ID3 标题/歌手 |
| 节拍器 | 浏览器 Web Audio API | 前瞻调度，详见下文 |
| 进程监控 | psutil | 后端诊断日志 |

**架构示意**

```
浏览器（React）
  │  REST /api/*           音频流 GET /api/audio/...（支持 Range 拖动）
  ▼
FastAPI（backend/app/main.py）
  ├─ 静态托管 frontend/dist（生产模式单端口）
  ├─ 上传/歌曲/推荐/变速/音频 REST API（app/api/*）
  ├─ 异步任务队列（services/tasks.py，进程内线程池，限并发）
  │     ├─ BPM 分析任务 → services/bpm.py（librosa）
  │     └─ 变速任务     → services/processor.py → ffmpeg_tools.py（atempo）
  └─ SQLite（database.py）  磁盘文件（songs / processing_tasks）
```

## 安装与启动

### 1. 安装依赖

```bash
# 后端
cd backend
python -m pip install -r requirements.txt

# 前端（仅开发需要）
cd ../frontend
npm install
```

### 2. 启动

**方式 A：开发模式（前后端分离，推荐改代码时用）**

```bash
# 终端 1 —— 后端（API）
cd backend
python run.py            # 0.0.0.0:8000

# 终端 2 —— 前端（热更新）
cd frontend
npm run dev              # http://localhost:5173 ，/api 自动代理到 8000
```

**方式 B：生产模式（单端口，无需 Node，部署/演示用）**

```bash
cd frontend
npm run build            # 生成 frontend/dist
cd ../backend
python run.py            # http://<本机IP>:8000 直接是完整应用
```

`run.py` 默认监听 `0.0.0.0`（方便手机/局域网访问）；只想本机访问：

```bash
python run.py 127.0.0.1
```

> ⚠️ **不要用多 worker 跑 uvicorn**：任务队列在进程内（内存），多进程会重复处理。
> systemd/nginx 模板里都已按单进程配置。

## 局域网手机访问

跑步场景用手机最方便，同一 WiFi 下：

1. 后端以默认 `0.0.0.0` 启动（方式 B 或 A 都行）。
2. 查电脑局域网 IP：`ipconfig`（无线局域网适配器 WLAN 的 IPv4，形如 `192.168.x.x`）。
3. 手机浏览器打开 `http://<电脑IP>:8000`。

Windows 若手机打不开，一般是防火墙拦了 8000，需要**新建入站允许规则**：

```powershell
netsh advfirewall firewall add rule name="RunBPM 8000" dir=in action=allow protocol=TCP localport=8000
```

（提示无权限时，用管理员 PowerShell 执行，或通过 Windows 安全中心→防火墙→高级设置添加。）

> 手机访问需与电脑同一网络；公司/校园网等隔离环境可能互相不通。

## 部署到云服务器（给其他人使用）

买好服务器后，项目自带全套部署文件，三分钟上线：

| 文件 | 作用 |
|---|---|
| `deploy/setup.sh` | Ubuntu/Debian 一键部署：装依赖 → venv → pip 包 → systemd 服务 → 防火墙 |
| `deploy/runbpm.service` | systemd 常驻服务：崩溃自重启、开机自启、数据目录独立于代码 |
| `deploy/nginx.conf.example` | 可选：域名 + HTTPS 反代模板（内含 basic auth 加密码示例） |
| `deploy/部署说明.md` | **完整中文指南**：打包、上传、部署、安全组、HTTPS、运维、备份、FAQ |

**三步速览**

```powershell
# ① Windows（PowerShell，在桌面目录）打包 —— 已排除本机数据/node_modules/.git
cd C:\Users\123\Desktop
tar -czf runbpm-deploy.tar.gz --exclude='muzrun/backend/data' --exclude='muzrun/frontend/node_modules' --exclude='muzrun/sandbox' --exclude='muzrun/.git' muzrun
scp runbpm-deploy.tar.gz root@你的服务器IP:/tmp/
```

```bash
# ② SSH 登录服务器
mkdir -p /opt/runbpm
tar -xzf /tmp/runbpm-deploy.tar.gz -C /opt/runbpm --strip-components=1
cd /opt/runbpm && sudo bash deploy/setup.sh
```

```bash
# ③ 云厂商控制台 → 安全组 → 入方向 → 放行 TCP 8000（最容易漏的一步）
#    然后所有人访问 http://服务器IP:8000
```

**注意事项**

- 服务器建议 Ubuntu 22.04/24.04、内存 ≥2GB（1GB 也能跑，脚本已默认分析并发=1）。
- 应用**没有登录鉴权**：网址公开后任何人都能上传歌曲并占用 CPU。只给熟人用，
  建议按 `deploy/nginx.conf.example` 里的注释加 basic auth 密码。
- 所有数据在 `/opt/runbpm/data`，升级代码不会丢；备份只需打包该目录。
- 升级代码：本机重新 `npm run build` → 重新打包上传解压覆盖 → `sudo systemctl restart runbpm`。
- 日志：`sudo journalctl -u runbpm -f`。

详细步骤、HTTPS、密码、CentOS/宝塔差异见 **[deploy/部署说明.md](deploy/部署说明.md)**。

## 使用手册

### 第 1 步：上传音乐

拖拽或点击上传区，可多选。上传后自动排队分析 BPM，页面右上角实时显示进度。

### 第 2 步：等分析 / 必要时手动修正

- 每首歌在列表里显示：标题、歌手、时长、**BPM、可信度**。
- 可信度低或明显测错：**直接点 BPM 数字**改成正确的值即可。
- 分析失败：点「重试」。

### 第 3 步：选运动模式

- **拖动滑杆**在四个区间里选节奏（走路/慢跑/跑步/快跑，滑杆本身就是彩色分段）；
- 或点下面的**四张区间卡**一键跳档；
- 想要 100 以下 / 185 以上等任意值：在右上角**输入框手动输**（40–300）。

### 第 4 步：生成推荐

点「生成推荐」。规则透明：按**每首歌离目标的相对差距**排序，越近越靠前。

读一行推荐：

```
  #  标题                 原BPM(相对目标)  方向   百分比
  1  Song A               155+5            ↑      +3.2%    ← 全部绿色 = 很接近
  2  Song B               155+8            ↑↑…     ...
  ✕  某首歌               155+23           ✕      +14.8%   ← 红色 ✕：差距>12%，不适合变速，自动不勾
```

- `155+5` = 目标 155、这首歌 160（高出 5）；`155-5` = 150，要提速。
- 百分比带符号：`+` 表示要放慢、`-` 表示要加快。
- 颜色：差距 **<5% 绿 / 5–8% 琥珀 / >8% 红**；✕ 表示 >12% 建议别选。
- **可变速的歌已自动勾选**；点行可切换勾选；「全选/全不选」只管可变速项。

### 第 5 步：变速并播放

点「▶ 变速并播放（n 首）」。后端把每首拉伸/压缩到目标 BPM（保持音高），
完成后**自动开始连续播放**整个列表，播完自动循环。

### 第 6 步：播放条上手

底部固定播放条（手机上也是固定的），从上到下：

1. **拍点标尺**（常驻）：绿线 = 拍点，随播放从右向左流过**中心线**（=当前时刻）；
   中心线正对的绿线就是「现在这一拍」。黄条 = 你打拍留下的痕迹。
2. **进度条**：拖动跳转；两侧是当前时间/总时长。
3. **歌曲信息 + 传输键**：标题 / 歌手 / `原BPM → 目标BPM` / 差距箭头；上一首 ·
   播放/暂停（圆形大键）· 下一首；「🥁 节拍器」开关（默认开）。
4. **音量区**：`🔊 音乐` 与 `🥁 拍子` 音量并排一行；`🎯 偏差` 单独一行。
5. **节拍设置**（节拍器开着时才显示）：
   - **拍点模式**：固定拍子（默认）/ 轻跟随 / 跟随起音
   - **校准区**（详见下节）
6. 若某首歌自动相位判断不可靠，会显示琥珀色「⚠ 相位可靠性低」，建议手动校准。

### 第 7 步：打拍校准（对不上时用这个）

自动对齐大部分歌很准；万一不对，**别猜，打拍**：

```
校准                              🔊 音效 关   👆 点按打拍   ← 大按钮在右侧，拇指位
BPM [输入框]  [设置（3/8）]  [🎯 设首拍]  [复位]
```

**基本流程（只听/只看节拍，不动首拍）**

1. 音乐播着，跟着鼓点连点 **👆 点按打拍**。每点一下：标尺多一条**黄条**、
   若音效开着会听到一声高音「滴」（G6，和节拍器的 D6「嗒」明显区分）。
2. 点满 **8 下**：取相邻间隔的**中位数**算出 BPM，自动填进 `BPM` 输入框
   （只是填进去，**不会立即生效**）。
3. 按 **设置（8/8）** 应用。整个拍点网格立刻按这个 BPM 重建（按钮上的
   `n/8` 进度始终可见，不点按打拍时显示 0/8）。

**把「第一拍」也对齐（相位）**

1. 先点 **🎯 设首拍** 把它打开（变黄 = 开）。
2. 在音乐**某一拍的准确位置**点一下 **👆 点按打拍**：当前位置立即被设为首拍，
   整个网格从这一拍开始重建——不用等 8 下。
3. 感觉整体还差一点点：用 **🎯 偏差**滑杆 ±平移（或拖到 0 按「归零」）。

**复位**：回到自动检测的拍点（清掉手动 BPM 与首拍）。

> 为什么打拍管用？你的耳朵比任何算法都可靠。8 下取中位数能抗手抖；
> 首拍对准后，网格就是「速度 × 相位」两个参数，比你看到的任何「偏移调整」都精确。

### 第 8 步：偏差微调与所见即所听

- 「🎯 偏差」滑杆范围 **−50% ~ +50% 拍距**（比如 155 BPM 一拍 0.387 秒，±50% ≈ ±0.19 秒）。
- 拖动时：**标尺绿条实时整体平移** + 节拍器点击同步平移——眼睛看到多少，耳朵就听到多少。
- 数值显示带方向（`+12% 滞后` / `-8% 提前`），非零时黄色高亮，「归零」一键还原。

## 拍点对齐系统（原理深挖）

这是全项目最「讲究」的部分，值得单独讲清楚。

### 为什么不能只靠 BPM？

节拍器要落在**音乐真实的每一拍**上。若只知道 BPM 而从 0 秒硬排：
(1) 不知道第一拍在哪（相位未知）；(2) 真实歌曲的瞬时节奏有起伏，固定间隔会越走越偏。
本项目因此为每首歌记录**全曲每个拍点的时刻**（节拍地图），节拍器逐拍点击。

### 分析时（services/bpm.py）做了什么

1. 用 librosa 算出**起始包络（onset envelope）**；
2. 锁定 DP 追踪器找出节拍序列 → 用**能量和最大化**确定主起音的相位；
3. 加权最小二乘拟合**周期 + 相位**（3 轮稳健迭代）；
4. **八度修正**：检测结果若约为真实速度的 2 倍 / 1.5 倍 / 0.5 倍，按规则折回合理区间；
5. 同时生成三种**节拍模式**的完整时间数组（原始时间轴）：
   - `grid`（固定拍子）：完全等距，默认推荐；
   - `light`（轻跟随）：每拍可在等距点 ±5% 内贴向实际起音；
   - `snap`（跟随起音）：±12% 内吸附打击点；
6. 用**两个独立相位信号**（通量法 vs 能量法）做交叉验证，输出 0–1 的
   **相位可靠性**——低则前端提示「建议手动校准」；
7. BPM 结果保留 1 位小数入库，供推荐排序。

### 变速后如何保证拍点仍然正确？

变速 ≠ 简单换速：FFmpeg 重采样后音频长度并非精确等于 原长×ratio。
所以处理流程是：**拉伸 → 对结果重新分析 → 用测量的时长比
`d_orig/d_proc` 把原节拍地图精确换算到新时间轴**（而非依赖理论比值），
消除了 atempo 的微小比例误差，拍点零漂移。验收指标：处理后再检测的 BPM
落在目标的最佳整数倍 ±5% 内，周期漂移 ≤0.24%。

### 播放时前端怎么选拍点（activeBeatMap 优先级）

```
① 手动校准（打了拍/填了 BPM/设了首拍）  → 前端当场重建等距网格，立即生效
② 处理后文件自带的节拍地图（当前模式）  → 正在播放的内容的地面真值
③ 原曲节拍地图 ÷ 变速比换算             → 兜底
```

手动校准永远优先：`BPM 输入框或设置按钮` 决定速度，`🎯 设首拍` 决定的时刻作锚点，
从锚点起按周期生成整条网格（与目标 BPM 无关，直接用你测的 BPM）。

## 节拍器实现细节

文件：`frontend/src/lib/metronome.ts`（约 250 行，核心全部在这）。

- **时间轴模型**：拍点活在**媒体时间轴**上（`第 n 拍 = phase + n×间隔`）。
- **前瞻调度**：每 25ms 检查一次，把接下来 250ms 内该响的拍子排进 AudioContext：
  `ctxTime = ctx.currentTime + (mediaTime − audio.currentTime)`。
  因此无论何时创建音频上下文、是否拖动进度、是否切歌，点击都精确落在音乐拍点上。
- **逐拍走地图**：命中地图里的真实拍点；地图用完则按最后间隔外推（到歌曲末尾为止）。
- **瞬时停止**：每个排程点击都登记；关闭节拍器/暂停/卡顿时立即取消未响的点击，
  没有「幽灵嗒」。
- **卡顿保护**：音频元素异常卡住时未响点击会堆积，设了 300 上限兜底。
- **音色**：D6（1174 Hz）方波 + 80ms 指数衰减，响度 = 音量 × 0.85
  （内部增益抬升，让默认 0.5 的音量滑块既清晰又有上下余量）。
- **打拍滴答**：独立的小 AudioContext，G6（1568 Hz）、50ms 短音——**高一个音**，
  打拍声和节拍器的「嗒」不会混；默认关闭（🔊 音效 开关），选择本地记忆。
- **拍点模式/相位微调/音效**等偏好各自持久化在 `localStorage`
  （`runbpm.beatMode` / `runbpm.phaseNudge` / `runbpm.tapSound`）。

**标尺（BeatRuler）**：每拍一根 2px 绿线，按 `t×80px/秒` 定位；播放时只更新一整个
容器的一次 CSS transform（`translateX(50% − now×80px)`），逐帧合成、绝无闪烁。
偏差滑杆改动时，绿条用**与节拍器完全相同的偏移量**重排——所见即所听。
（打拍黄条是 3px 琥珀线，保留最近 20 个，不随播放清除。）

## 音频处理与磁盘缓存

| 环节 | 工具 | 说明 |
|---|---|---|
| 解码/重采样 | FFmpeg / soundfile | M4A/AAC 等自动走 FFmpeg 解码 |
| BPM 分析 | librosa | 22.05 kHz、上限 600 秒窗口 |
| 时长探测 | librosa 优先，FFmpeg 兜底 | |
| 元数据 | mutagen | ID3 标题/歌手 |
| 变速 | FFmpeg `atempo` | 每级 0.5–2.0，超范围自动拆成多级链 |

**缓存键**：`processed/{song_id}__{目标BPM}.mp3`。同一首歌再次要求相同目标 BPM
直接复用文件；数据库任务表记录每次处理（含处理后的 BPM 与节拍地图，供回放对齐）。

**并发**：分析默认 2 路、变速默认 1 路（`RUNBPM_MAX_CONCURRENT_*` 可调）；队列上限
300 个待办。删除歌曲时调用 `cleanup_song_files` 清理原始文件、缓存与任务。

## 常见问题

**部署 / 访问**

- 服务器手机打不开，服务器上 `curl http://127.0.0.1:8000/api/health` 却是好的 →
  云厂商**安全组**没放行 8000（控制台 → 安全组 → 入方向规则 → TCP 8000）。
- 手机打不开局域网地址 → 同 WiFi？Windows 防火墙放行 8000 了吗（见第 7 节）？
  校园网/公司网可能互相隔离。
- 页面是旧版本 → 浏览器缓存，强制刷新（Ctrl+F5；手机清缓存或开无痕）。
- 想加访问密码 → 看 `deploy/nginx.conf.example` 里 `auth_basic` 注释。

**上传 / 分析**

- 「不支持的文件类型」→ 只支持 MP3/WAV/M4A/AAC/OGG/FLAC/OPUS，看扩展名。
- 「文件过大」→ 默认 100MB，`RUNBPM_MAX_UPLOAD_MB` 调大。
- 「无法可靠检测 BPM」→ 音频太短或节奏太自由；重试，或直接在表里手改 BPM。
- 分析很慢 → 服务器/电脑内存小；把 `RUNBPM_MAX_CONCURRENT_ANALYZE` 降到 1。

**变速 / 播放**

- 变速失败 → 差距超出 1/3×–3× 会拒绝（防严重失真）；换个更接近的目标 BPM，
  或先手动修正歌曲 BPM。
- 浏览器不自动播放 → 首次「变速并播放」是用户手势一般没事；被拦截就手动点播放键。
- 处理完没声音但进度在走 → 音量滑杆？浏览器音频策略？

**节拍 / 校准**

- 节拍器没声音 → Web Audio 需浏览器支持；确认「🥁 节拍器」开着、拍子音量 > 0；
  若刚开没声，点一下播放/暂停触发恢复。
- 自动对齐偏一点 → 先用 **🎯 偏差**滑杆整体平移（绿条实时可见）；仍不行再做打拍校准。
- 打拍后 BPM 没变 → 打满 8 下只是**填进输入框**，要点「设置（8/8）」才生效；
  或直接用输入框手输后按回车/失焦。
- 打拍没声音 → 「🔊 音效」开关默认关，手动打开（偏好会记住）。
- 相位可靠性低警告 → 表示两个独立信号对拍点判断不一致，自动对齐可能不准，
  按第 7 步手动校准最稳。
- 黄条太多看不清绿线 → 黄条只保留最近 20 个，继续打拍旧的会被挤掉。

**ffmpeg**

- ffmpeg 相关报错 → 默认走 imageio-ffmpeg 自带静态构建，无需安装；
  若自定义了 `RUNBPM_FFMPEG_PATH` 请确认路径；Linux 上如 pip 装完仍找不到，
  可 `apt install ffmpeg` 让它走 PATH。

## 隐私与版权边界

本项目只处理**用户自己上传的音乐文件**：分析、变速、播放全部在本机/自有服务器完成，
不上传任何第三方、不抓取音乐平台的受保护音频、不对外公开传播。上传内容仅用于个人
跑步训练场景。
